Abstract

Memory decides which LLMs an edge device runs, and how fast: capacity on a 4 GB Jetson Nano, bandwidth on an 8 GB Jetson Orin Nano Super. Deployed formats (GPTQ, AWQ, llama.cpp's K- and I-quants) spend equal bits on every integer code of a matrix, although the codes are far from uniform.

LazyWeights keeps these formats but tunes GPTQ so the codes compress, Huffman-codes them losslessly in interleaved lanes, and decodes them on demand in a small unit between DRAM and L2, so GPU kernels run unchanged and DRAM moves only coded bytes. At 1% and 3.5% perplexity budgets, coded Phi-3-mini, Mistral-7B and SmolLM-1.7B are 5.7–31.4% smaller than the best llama.cpp format.

A bit-exact 0.21 mm2 ASIC decoder unit (1 GHz, 7 nm) cuts Orin latency and energy per token by up to 36% and 38% (54% and 44% with prompt-lookup speculation). On the Nano, LazyWeights needs 58–64% less time and 53–57% less energy per token than CPU llama.cpp, and runs a streamed Mistral-7B 6.6× faster at 3.89 bits per weight. A Huffman decoder beats an rANS decoder in rate and area at equal throughput; the ASIC decoder unit runs bit-exact on a Zynq UltraScale+ FPGA (AMD ZCU102).

Equal bits for unequal codes

On the edge, memory is the bottleneck twice over. The 4 GB Jetson Nano cannot even hold Mistral-7B, and the 8 GB Orin Nano Super is bound by DRAM bandwidth. Every deployed weight format, llama.cpp's K- and I-quants included, gives each integer code the same width, although the codes of a matrix are far from uniform. LazyWeights spends the bits where the information is: it keeps the format, steers the codes toward a concentrated histogram, and codes them losslessly.

Fig. 2. Code selection (histograms illustrative). LazyWeights keeps the format but shares one step per super-block (γ) and widens it (c), so the codes concentrate. GPTQ feeds each column's error to the remaining columns, so the coarser grid keeps its quality.

1 · Select the codes

scripts/kq_quant.py

GPTQ runs into llama.cpp's own block formats (Q4_K, Q5_K, Q6_K, IQ4_XS), so the output is a valid GGUF that unmodified llama.cpp loads. One shared, widened step per super-block concentrates the codes; an optional entropy term joins GPTQ's code choice.

2 · Code them

lazyweights/bundle.py

Each matrix gets one length-limited Huffman table (11-bit codes). A 64×256 tile is 32 lanes of two rows, with the lanes' 32-bit words interleaved, so one aligned read fetches the next word of every lane. 4-bit codes are coded in pairs. Scales and minimums stay as llama.cpp stores them.

3 · Decode on demand

hw/huff/rtl

A decode unit between the memory controller and L2 restores the packed codes, so GPU kernels run unchanged and DRAM moves only coded bytes. Each lane compares an 11-bit peek against per-length limits, so there is no 2048-entry lookup table.

The bundle and the decode unit

Fig. 3. (a) Bundle layout: each lane is one Huffman stream of 32-bit words; the lanes' words are interleaved, so one aligned read fetches the next word of every lane, and per-tile lane offsets let any tile start on its own. (b) The decode unit: T engines of 32 lanes share an 8-word read port through a masked round-robin arbiter. Each lane adds the code length's offset to index the symbol table and shifts its buffer by the length.

The runtime that runs the coded models on the Jetsons (kernels/llmrt.cu) fuses decode with GEMV, captures each pass in CUDA graphs, and supports prompt-lookup speculation and streaming from USB 3. Where the decode unit is not in silicon, the runtime stands in for it with software decode, or with a decode-free fixed-width “twin” whose measured time is used as the unit's.

Logic synthesis, pre-layout (Table V). † after OpenROAD repair. The Orin's four-engine unit is 0.206 mm2; the Nano needs one engine.

Comparators, not tables. A 2048-entry lookup table per lane is nine times the area of a lane that compares an 11-bit peek against per-length limits, and it misses timing by 31 ns.

Huffman over rANS. rANS is never smaller (0.0 to +1.0% more bits), and at equal throughput (2 G weights/s) it needs 4.0× the area with pair symbols, or 1.15× with single codes.

On an FPGA, bit for bit. On the AMD ZCU102, four engines close timing at 112.5 MHz. All 29 matrices (484M weights) decode bit-exact, with cycle, stall and word counts equal to the C model on every chunk: 14.3 G weights/s at 0.26 nJ per weight.
